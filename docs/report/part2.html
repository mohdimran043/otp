Decoding a frame is the most expensive thing the system does — locating four fiducials, fitting a homography, sampling every cell, demodulating, then checking a CRC32 and a SHA-256. Measured on one core:

The striking result is that throughput per core is roughly constant — 85 to 115 KB/s — whatever the geometry. Bigger frames take proportionally longer. So the receiving side's capacity is essentially cores × 100 KB/s, and the frame rate that makes sense follows from it:

frames per second = decode workers × 115 000 ÷ bytes per frame

Frames are decoded concurrently, one worker per core less one. Everything after the decode stays strictly sequential — chunk records, acknowledgements, the final merge — so no locking was introduced and the ordering guarantees are unchanged.

Prefer fewer, larger frames. Twice the throughput at less than two thirds the frame rate. Every frame costs a fixed overhead — a file read, an image decode, a database row, an acknowledgement — regardless of how much payload it carries, so larger frames amortise all of it. This was not the expected result and is the most useful tuning lesson the project produced.

4 · What a chunk actually is

A file does not cross as a file. It is compressed, cut into chunks sized so that exactly one chunk fills exactly one frame, given error-correction shards their own frames, and rendered.

The anatomy of one frame

┌─────────────────────────────────────────────────────────┐
│ ▣                  HEADER BAND                       ▣  │  ← always black & white
│                  (always binary)                        │     whatever the payload is
├─────────────────────────────────────────────────────────┤
│ │                                                     │ │
│ │              MODULATED PAYLOAD                      │ │  ← 1–4 bits per cell
│t│         1 903 bytes at color8 / 96×96               │t│     depending on encoding
│i│                                                     │i│
│m│                                                     │m│
├─────────────────────────────────────────────────────────┤
│ ▣            FOOTER: CRC32 + SHA-256                 ▣  │  ← integrity of the payload
└─────────────────────────────────────────────────────────┘
  ▣ = one of four corner fiducials (7×7 concentric squares)
  t/i = timing columns down each side

Four design decisions are worth drawing out, because each one earns its cost:

  • Four corner fiducials, not three. QR codes use three, which fixes rotation and scale. Four supply the correspondences for a full homography — so a camera mounted genuinely off-axis is corrected rather than merely tolerated.
  • The header and footer are always plain black and white, whatever modulation the payload uses. This is what lets a receiver read a frame it knows nothing about: it learns the geometry and the encoding from the frame, and only then demodulates the payload.
  • The footer carries both a CRC32 and a SHA-256 of the payload. The CRC is cheap and catches ordinary corruption; the hash makes a frame that satisfies it essentially certain to be intact.
  • Timing columns down each side let the decoder track cell boundaries across the frame rather than trusting a single global grid estimate.
