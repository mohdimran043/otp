Summary for management

QuestionAnswer
Does it work?Yes, and it is verified rather than asserted. Every transfer is checked against a hash computed before anything was drawn, and the receiving endpoint recomputes it independently. Tested eleven ways end to end, including one frame in three deliberately destroyed.
How fast?1.45 MB/s measured on one monitor and one camera — 8 MB of incompressible data in 5.5 seconds, zero retransmissions. Roughly 1 GB in 12 minutes.
Can it go faster?Yes, and the route is horizontal: several screen–camera pairs carrying different chunks of the same file. Three pairs ≈ 6.6 MB/s. The design already supports it; the work is small (§8).
Can data be lost?No. A chunk is shown repeatedly until the far side confirms it arrived intact. There is no path by which the sender moves on from an unconfirmed chunk.
What hardware?A 4K monitor, a 1080p webcam, and a machine with cores to spare. No specialist equipment; both sides ran in containers on ordinary hardware for every figure in this document.
Biggest limitation?Decoding cost — about 100 KB/s per CPU core, whatever the settings. The receiving side's core count sets the ceiling, which is why scale-out is the answer rather than tuning.
Not yet built?Authentication on both APIs, and the multi-pair scale-out of §8. Both are named plainly here rather than left to be discovered.

The one idea to take away. Light only travels one way, and a frame lost to a flicker or a hand across the lens produces no error — only silence. So the sender never waits for bad news. It waits for good news, over a separate channel, and does not move on without it. Everything else in the system is an optimisation on top of that one rule.
