5 · How the settings control what is generated

Five independent choices, all on the sender's Settings page, and each changes the bytes that end up on screen. The header records every one of them, so the receiver never has to be told separately.

SettingOptionsWhat it changesWhen it may change
Encodingbinary, grayscale, color8, color16, rollingBits per cell: 1 → 4. Directly multiplies capacityOnly between transfers
Grid96×96 … 512×512Cells per frame, so bytes per frameOnly between transfers
Cell size4 – 8 pxScreen area and the camera's blur budget. Not capacityOnly between transfers

Frame rate1 – 480 fpsHow fast frames are shown. Nothing about their contentAny time, mid-transfer

Why geometry cannot change mid-transfer, and frame rate can. The grid, cell size and encoding are written into every frame header, and the chunk size was derived from the encoder's capacity at that grid. Changing them halfway would render the remaining chunks to a shape the manifest never declared, and the receiver would reassemble the wrong file. The system refuses it while anything is in flight and says so.

The frame rate is only a delay between two writes. Nothing already rendered depends on it, so it applies on the next frame — which is exactly when an operator wants it, because a receiver falling behind is the reason to turn it down.

How a change of algorithm changes the code on screen

The same 1 903 bytes of payload, drawn five different ways. The choice is visible at a glance:

Two of these are worth a sentence of explanation for a non-specialist audience:

  • color8 is the workhorse. Eight fully saturated colours are far apart in colour space, so a lens that blurs and a sensor that adds noise still leave them distinguishable. It carries three times what black-and-white does at no cost in reliability.
  • color16 is the fast one and the fragile one. Sixteen levels means telling apart four brightnesses of twelve hues, which needs either a controlled installation or — as in the HTTP transport, where frames are fetched rather than photographed — no optics at all.

6 · How the receiver is told which algorithm was used

Two mechanisms, at different scales, and the distinction matters.

Per frame: the header

Every frame states its own encoding, bit depth, geometry, compression and error-correction identifiers, in a band that is always plain black and white. So a receiver that has just been switched on, knowing nothing, can read any frame it happens to catch: read the binary header, learn how the rest of this image is modulated, then demodulate it. Nothing has to be configured on the receiving side to match the sender.

Per transfer: the manifest frame

A header describes one frame. It cannot say how big the whole file is, what it is called, or what it should hash to. That is the manifest — a frame of its own, marked with a flag, sent first and then re-sent periodically so that a receiver joining late can still catch up.

Why the callback URL travels across the gap. The sending side is where a caller supplies it, and the receiving side is the one that ends up holding a finished file. It arrives from outside the receiver's trust boundary, so delivery is gated by an allowlist the receiving operator controls, and redirects are not followed — a redirect would be the far side choosing a second destination after the first had been approved.
