Moving large files across an air gap
with a monitor and a camera

A technical overview of the Optical Transport Platform: what it does, how fast it goes, and what governs both.

Measured on commodity hardware — a 20-core workstation and an integrated 1080p webcam. Every figure in this document comes from a test in the repository, not an estimate.

Summary for management

QuestionAnswer
Does it work?Yes, and it is verified rather than asserted. Every transfer is checked against a hash computed before anything was drawn, and the receiving endpoint recomputes it independently. Tested eleven ways end to end, including one frame in three deliberately destroyed.
How fast?1.45 MB/s measured on one monitor and one camera — 8 MB of incompressible data in 5.5 seconds, zero retransmissions. Roughly 1 GB in 12 minutes.
Can it go faster?Yes, and the route is horizontal: several screen–camera pairs carrying different chunks of the same file. Three pairs ≈ 6.6 MB/s. The design already supports it; the work is small (§8).
Can data be lost?No. A chunk is shown repeatedly until the far side confirms it arrived intact. There is no path by which the sender moves on from an unconfirmed chunk.
What hardware?A 4K monitor, a 1080p webcam, and a machine with cores to spare. No specialist equipment; both sides ran in containers on ordinary hardware for every figure in this document.
Biggest limitation?Decoding cost — about 100 KB/s per CPU core, whatever the settings. The receiving side's core count sets the ceiling, which is why scale-out is the answer rather than tuning.
Not yet built?Authentication on both APIs, and the multi-pair scale-out of §8. Both are named plainly here rather than left to be discovered.

The one idea to take away. Light only travels one way, and a frame lost to a flicker or a hand across the lens produces no error — only silence. So the sender never waits for bad news. It waits for good news, over a separate channel, and does not move on without it. Everything else in the system is an optimisation on top of that one rule.

1 · What the system is

Two computers with no network between them. One displays a file as a sequence of encoded images; the other photographs them and reassembles the file, then verifies it against a cryptographic hash the sending side declared before anything was drawn.

The only channel between them that is not optical carries acknowledgements — small signed records saying "chunk 47 arrived intact". That return path is what turns a hopeful broadcast into a lossless transfer, and it is the single most important idea in the design.

Figure 1. Data crosses as light and cannot be acknowledged optically — a lost frame produces no report, only silence. So the return path carries the acknowledgements, and the sender never advances past a chunk it has not heard about.

The guarantee, in one sentence. A chunk is displayed repeatedly until a signed acknowledgement for it arrives. Nothing else in the system promises delivery; error correction is an optimisation on top of that, not the guarantee.

Refresh rate is a ceiling, not a target

A 144 Hz panel can show 144 frames a second. Setting the sender to 144 fps does not transfer 144 frames' worth of data, because the receiver cannot read that fast — and a frame nobody reads costs a render and delivers nothing. The panel's rate is measured in the browser on the Settings page (requestAnimationFrame intervals; 144 Hz shows as 6.94 ms) and offered as an upper bound.

The striking result is that throughput per core is roughly constant — 85 to 115 KB/s — whatever the geometry. Bigger frames take proportionally longer. So the receiving side's capacity is essentially cores × 100 KB/s, and the frame rate that makes sense follows from it:

frames per second = decode workers × 115 000 ÷ bytes per frame

Frames are decoded concurrently, one worker per core less one. Everything after the decode stays strictly sequential — chunk records, acknowledgements, the final merge — so no locking was introduced and the ordering guarantees are unchanged.

Prefer fewer, larger frames. Twice the throughput at less than two thirds the frame rate. Every frame costs a fixed overhead — a file read, an image decode, a database row, an acknowledgement — regardless of how much payload it carries, so larger frames amortise all of it. This was not the expected result and is the most useful tuning lesson the project produced.

4 · What a chunk actually is

A file does not cross as a file. It is compressed, cut into chunks sized so that exactly one chunk fills exactly one frame, given error-correction shards their own frames, and rendered.

Figure 2. A real chunk frame from a transfer: 96×96 cells at 6 px, color8, three bits per cell, 1 903 payload bytes.

Figure 3. The manifest frame from the same transfer. Same geometry, different content — this is the frame that tells the receiver what everything else means.

The anatomy of one frame

┌─────────────────────────────────────────────────────────┐
│ ▣                  HEADER BAND                       ▣  │  ← always black & white
│                  (always binary)                        │     whatever the payload is
├─────────────────────────────────────────────────────────┤
│ │                                                     │ │
│ │              MODULATED PAYLOAD                      │ │  ← 1–4 bits per cell
│t│         1 903 bytes at color8 / 96×96               │t│     depending on encoding
│i│                                                     │i│
│m│                                                     │m│
├─────────────────────────────────────────────────────────┤
│ ▣            FOOTER: CRC32 + SHA-256                 ▣  │  ← integrity of the payload
└─────────────────────────────────────────────────────────┘
  ▣ = one of four corner fiducials (7×7 concentric squares)
  t/i = timing columns down each side

Four design decisions are worth drawing out, because each one earns its cost:

  • Four corner fiducials, not three. QR codes use three, which fixes rotation and scale. Four supply the correspondences for a full homography — so a camera mounted genuinely off-axis is corrected rather than merely tolerated.
  • The header and footer are always plain black and white, whatever modulation the payload uses. This is what lets a receiver read a frame it knows nothing about: it learns the geometry and the encoding from the frame, and only then demodulates the payload.
  • The footer carries both a CRC32 and a SHA-256 of the payload. The CRC is cheap and catches ordinary corruption; the hash makes a frame that satisfies it essentially certain to be intact.
  • Timing columns down each side let the decoder track cell boundaries across the frame rather than trusting a single global grid estimate.

5 · How the settings control what is generated

Five independent choices, all on the sender's Settings page, and each changes the bytes that end up on screen. The header records every one of them, so the receiver never has to be told separately.

SettingOptionsWhat it changesWhen it may change
Encodingbinary, grayscale, color8, color16, rollingBits per cell: 1 → 4. Directly multiplies capacityOnly between transfers
Grid96×96 … 512×512Cells per frame, so bytes per frameOnly between transfers
Cell size4 – 8 pxScreen area and the camera's blur budget. Not capacityOnly between transfers
Compressionnone, gzip, lz4, zstd, brotliHow much file becomes how many chunksPer transfer
Error correctionnone, Reed–Solomon, RaptorQ, LDPCHow many extra parity frames are shownPer transfer
Frame rate1 – 480 fpsHow fast frames are shown. Nothing about their contentAny time, mid-transfer

Why geometry cannot change mid-transfer, and frame rate can. The grid, cell size and encoding are written into every frame header, and the chunk size was derived from the encoder's capacity at that grid. Changing them halfway would render the remaining chunks to a shape the manifest never declared, and the receiver would reassemble the wrong file. The system refuses it while anything is in flight and says so.

The frame rate is only a delay between two writes. Nothing already rendered depends on it, so it applies on the next frame — which is exactly when an operator wants it, because a receiver falling behind is the reason to turn it down.

Two of these are worth a sentence of explanation for a non-specialist audience:

  • color8 is the workhorse. Eight fully saturated colours are far apart in colour space, so a lens that blurs and a sensor that adds noise still leave them distinguishable. It carries three times what black-and-white does at no cost in reliability.
  • color16 is the fast one and the fragile one. Sixteen levels means telling apart four brightnesses of twelve hues, which needs either a controlled installation or — as in the HTTP transport, where frames are fetched rather than photographed — no optics at all.

6 · How the receiver is told which algorithm was used

Two mechanisms, at different scales, and the distinction matters.

Per frame: the header

Every frame states its own encoding, bit depth, geometry, compression and error-correction identifiers, in a band that is always plain black and white. So a receiver that has just been switched on, knowing nothing, can read any frame it happens to catch: read the binary header, learn how the rest of this image is modulated, then demodulate it. Nothing has to be configured on the receiving side to match the sender.

Per transfer: the manifest frame

A header describes one frame. It cannot say how big the whole file is, what it is called, or what it should hash to. That is the manifest — a frame of its own, marked with a flag, sent first and then re-sent periodically so that a receiver joining late can still catch up.

Manifest fieldWhat the receiver does with it
FilenameNames the reassembled file. Validated as a bare name, because it crosses from outside
OriginalSize, CompressedSizeBounds decompression — every codec here can expand a small input without limit
SHA256The verdict. Computed over the original file before anything was drawn
ChunkCount, ChunkSizeKnows how many pieces to expect and when it has them all

FEC (id, data shards, parity shards, shard size)How to rebuild a chunk that never arrived from the parity ones that did
CallbackURLWhere to deliver the finished file — checked against an operator-held allowlist

Why the callback URL travels across the gap. The sending side is where a caller supplies it, and the receiving side is the one that ends up holding a finished file. It arrives from outside the receiver's trust boundary, so delivery is gated by an allowlist the receiving operator controls, and redirects are not followed — a redirect would be the far side choosing a second destination after the first had been approved.

7 · What happens to a captured frame

Nine steps, in order. The order is the design: each one exists to stop a specific failure being mistaken for a different one.

Figure 4. The receiving pipeline. Steps 3–5 run on 19 cores in parallel; everything after the decode is strictly sequential, which is why no locking was needed.

Why "store before decoding"

Every captured image is written to disk before anything tries to read it. A frame that cannot be decoded is the primary evidence for why a camera is going badly — blur, a tear, a hand across the lens — and it is the only thing a replay can work from. Discarding it would throw away the diagnosis along with the frame.

Why a failed chunk gets no reply at all

This is the part that most often surprises people, and it is deliberate. A frame that fails its checksum is not reported. There is no negative acknowledgement.

A frame that could not be read cannot say which chunk it was carrying — that information was in the part that failed to decode. So there is nothing to send a complaint about. The sender learns of the failure by its acknowledgement timing out, and shows the chunk again. Waiting for good news is the only mechanism that can work here; waiting for bad news would mean waiting for a message that can never be composed.

The acknowledgement, and why the same chunk stops appearing

When a chunk passes both checksums, the receiver writes a small signed record:

{
  "transmission_id" : "1adc37ba-fb0d-4c1d-a80e-ad62e0250924",
  "chunk_number"    : 47,
  "status"          : "ok",
  "bit_error_rate"  : 0.0,
  "received_at"     : "2026-08-07T14:33:02.881Z"
}
   + HMAC-SHA256 over the exact bytes above

The sender reads it, marks chunk 47 acknowledged, and never displays it again. Three consequences follow, and together they are the whole delivery model:

  • The display converges. As acknowledgements arrive, the set of frames still worth showing shrinks. The display spends its time on what has not arrived rather than cycling through what has.
  • The display never idles. If everything in the current window is awaiting acknowledgement, the oldest outstanding frame is shown again — a camera pointed at a blank screen learns nothing.
  • A duplicate is not acknowledged twice. The sender already stopped showing that chunk and cannot un-know it, so a second record carries no information. Suppressing them was worth 4× in wall clock: a repeated five-transfer test went from 14.5 s to 3.4 s, and its rate stopped collapsing from 192 KB/s to 24 KB/s across runs.

The acknowledgement channel is the one input the sender takes from outside itself. Every record is signed with HMAC-SHA256 over its exact bytes, using a secret both sides hold and which has no default. Anything able to write that channel could otherwise report chunks as delivered when they were not — and the sender would move on, producing a file that is quietly incomplete.

8 · Going faster: many screens, many cameras, one database

A single monitor–camera pair is limited by the receiving machine's cores: roughly 100 KB/s per core, or 2.2 MB/s on the workstation measured here. The way past that is not a better camera. It is more pairs, running at once, carrying different chunks of the same file.

Figure 5. Horizontal scale-out. The database each side already holds one row per chunk, which is what makes disjoint claiming possible without inventing a new coordination mechanism.

Why the existing design already supports this

Three properties, all present today, are what make scale-out a matter of configuration rather than redesign:

  • A chunk is addressed by number, not by position in a stream. Chunk 47 is chunk 47 whichever screen showed it and whichever camera read it. Nothing about reassembly depends on the order frames arrive in.
  • The database already claims work atomically. The job engine uses SELECT … FOR UPDATE SKIP LOCKED, which is precisely the primitive needed: several display loops ask for the next unacknowledged chunk and each is handed a different one, with no lock contention and no double-showing.
  • Acknowledgements are per chunk and idempotent. Two channels cannot conflict, because the record says which chunk arrived and says nothing about who showed it.

What would need building

This is a proposal, not a shipped feature, and the honest scope is small but not nil:

WorkEffortWhy it is needed
Chunk-range claiming in the display loopSmallEach display asks the database for the next unacknowledged chunk rather than walking its own list
One receiver per camera, sharing a databaseSmallThe pipeline already writes chunk rows; several instances against one database need no change beyond configuration
Merge triggered by count, not by one processSmallWhichever receiver records the last chunk performs the merge; the others see it is done
Per-channel session accountingModerateSo an operator can see which screen–camera pair is underperforming rather than one blended figure

What it buys. Throughput becomes linear in the number of pairs, because the pairs share nothing but a database. Three pairs on the hardware measured here is roughly 6.6 MB/s — 1 GB in about two and a half minutes. Ten pairs, on ten inexpensive machines, would be about 22 MB/s: 1 GB in 45 seconds.

Where it stops being linear. The shared database becomes the coordination point, and at some number of pairs the acknowledgement write rate is the constraint rather than the cameras. On the figures measured here that point is a long way out — acknowledgements are a few hundred bytes and a few hundred per second per channel — but it is where the next ceiling lives, and it should be measured rather than assumed before anyone commits to a pair count.
